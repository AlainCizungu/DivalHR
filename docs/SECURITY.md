# DivalHR Security and Privacy Baseline

## Principles

- Deny by default.
- Enforce least privilege.
- Authenticate the actor and authorize the action at every boundary.
- Treat tenant context as verified security state.
- Minimize collection and disclosure.
- Require traceability for sensitive actions.
- Keep secrets out of source code, logs, analytics, and clients.

## Authentication

- OIDC for workforce authentication
- SAML support for enterprise customers
- MFA required for privileged roles
- Short-lived access tokens
- Secure recovery and session revocation
- Separate service credentials with scoped permissions

## Authorization

Use role-based access for understandable administration and attribute-based rules for sensitive conditions.

Relevant attributes include tenant, legal entity, site, department, manager relationship, worker relationship, data category, action, and elevated privilege.

## Platform-scoped versus tenant-scoped operations

Every non-public `/api/v1` operation, read or write, declares exactly one scope; a test fails the build otherwise, and a contract test checks each handler's scope and role against `x-divalhr-scope` and `x-divalhr-required-role`.

| | Platform-scoped (`@PlatformScoped`) | Tenant-scoped (`@TenantScoped`) |
|---|---|---|
| Purpose | Act across tenants, e.g. provisioning an organization (MVP-001) | Act inside one tenant |
| Who | `platform-admin` only (`x-divalhr-required-role` in the contract) | Users whose verified `tenant_id` owns the resource |
| Tenant source | Never the caller's `tenant_id` claim; new tenant IDs are generated by the server | Only the verified `tenant_id` claim, checked by `TenantAccessGuard` |
| Enforcement | MVC interceptor before the body is read, plus `@PreAuthorize("hasRole('platform-admin')")` | Tenant guard on every tenant-owned read and write |
| Denials | 403 `ACCESS_DENIED`, safe structured security log (`divalhr.security`), a `denied` metric and an append-only denial row (MVP-013) | 403 `TENANT_ACCESS_DENIED` |

A platform administrator gains **no** access to tenant-scoped resources of other tenants through the platform role. Both privileged roles also require multifactor assurance (MVP-011, below). Privileged authorization denials leave durable evidence (MVP-013, below).

### Verified subject (Issue #17)

Idempotency and audit are keyed on the verified JWT `sub`. For every `@PlatformScoped` or `@TenantScoped` handler, `ScopeAuthorizationInterceptor` first confirms the caller is a JWT with a non-blank `sub`; otherwise it answers `403 ACCESS_DENIED` before role, tenant, query, argument or body processing, writes one `divalhr.security` log entry (`reason=subject_missing`, operation, scope, required role, result, correlation ID; never the token, claims, body, idempotency key or subject) and records exactly one `denied` metric. Public endpoints are unaffected. Controller subject checks remain as defense in depth. Rejecting such tokens at JWT validation (a `401`) would be a separate contract decision.

### Operation names (Issue #17)

Idempotency operations and audit actions follow one grammar, `^[a-z]+(-[a-z]+)*(\.[a-z]+(-[a-z]+)*)+$`, defined once in `OperationName` and enforced by the database since V4.

### Tenant-administrator operations (MVP-002)

Legal-entity, region, site (including the first region assignment), department, cost-center and team endpoints use `@TenantAdminOperation`, which combines `@TenantScoped(role = "tenant-admin")` with `@PreAuthorize("hasRole('tenant-admin')")`. The interceptor rejects any other role with 403 `ACCESS_DENIED` before the body is read, then requires a valid `tenant_id` claim (403 `TENANT_CONTEXT_MISSING`). Employees and platform administrators are denied; there is no implicit platform access to tenant data.

- The tenant comes only from the verified token. Headers, query parameters and bodies never supply it; unknown body properties such as `tenantId` are rejected.
- Every repository method takes the verified `TenantId` and filters on it (enforced by an ArchUnit rule). A missing parent and another tenant's parent return the same `404 LEGAL_ENTITY_NOT_FOUND`, `404 SITE_NOT_FOUND`, `404 REGION_NOT_FOUND`, `404 DEPARTMENT_NOT_FOUND` or `404 COST_CENTER_NOT_FOUND` body, apart from `correlationId`. A team's site is derived from its verified parent, never read from the request.
- Only the named unique indexes map to `409 DUPLICATE_LEGAL_ENTITY_CODE` / `DUPLICATE_SITE_CODE`; every other database error is a generic `500 INTERNAL_ERROR`. Problem params never echo submitted names, codes, IDs, SQL, constraint names or cursors.
- PostgreSQL row-level security is not used in this increment; isolation relies on the tenant predicates, the composite foreign key and the tests above.

### Invitations and tenant memberships (MVP-010)

Tenant administrators invite people by email with exactly one tenant role. The invitation endpoints use `@TenantAdminOperation` like the hierarchy endpoints; employees and platform administrators are denied before the body is read.

- **Roles.** Only `tenant-admin` and `employee` can be assigned. `platform-admin` and any other value are rejected like an unknown role by the API (`400 VALIDATION_FAILED`, never echoed), by the database (`invitation_role_assignable`, `tenant_membership_role_assignable`) and by the identity provider (below).
- **Tenant.** Only from the verified token. The body is exactly `{email, role, locale}`; `tenantId` and any other property are rejected. Revoking or resending another tenant's invitation returns the same `404 INVITATION_NOT_FOUND` as a missing one. `409 INVITATION_ALREADY_PENDING` and `409 INVITATION_RECIPIENT_ALREADY_MEMBER` consult only the caller's own tenant; an address known elsewhere behaves like any other.
- **Personal data.** The invitee address is confidential. It never appears in logs, metrics, errors, audit metadata, outbox events or idempotency records: the create and resend responses are receipts without the address (replayed exactly, A2). Lookups use a keyed HMAC (`DIVALHR_EMAIL_LOOKUP_KEY`, at least 32 bytes, required at start-up; `dev-only-` values are refused outside development).
- **Quotas.** Per tenant: 50 invitations per hour and 500 open invitations (`429 INVITATION_RATE_LIMITED` with `Retry-After`). Per invitation: at most 3 reissues, at least 5 minutes apart (`429 INVITATION_RESEND_LIMITED`).
- **Delivery (A3).** Mail is sent once, after the transaction commits, and the result is recorded conditionally on the invitation and its issuance. `QUEUED` is shown as "invitation created, delivery pending", only `SENT` as "sent", and `FAILED` (including a delivery whose outcome stayed unknown for 10 minutes) as an actionable warning. Deliveries are never retried automatically; a resend issues a new link and invalidates the previous one. An earlier message may have reached the invitee, but only the newest link works.
- **Caching (guardrails 3 and 6).** Admin responses carry `Cache-Control: private, no-store`; public responses `Cache-Control: no-store`. The web app requests both with `cache: 'no-store'`, and the service worker has no runtime caching and never answers `/api/` navigations with the cached shell (`src/pwa/workbox.ts`, pinned by tests).

### Public invitation endpoints (MVP-010)

`POST /api/v1/public/invitations/inspect` and `/accept` are the only anonymous business endpoints. They run in their own filter chain (`/api/v1/public/**`, no resource server): bearer tokens are neither required nor read, every other method and path is denied, and each handler is marked `@PublicOperation` (checked against `x-divalhr-scope: public` by the contract test).

- **Token.** 32 random bytes, base64url (43 characters); only its SHA-256 is stored, and it is erased when the invitation reaches a terminal state. The link carries it in the URL fragment (`/invitation#token=…`), which browsers never send to a server; the page removes the fragment immediately, keeps the token in memory only and sends it only in POST bodies, through a client that never attaches an access token.
- **One answer for every unusable token.** Unknown, malformed, expired, revoked, replaced and used tokens all return the same `404 INVITATION_INVALID`. Inspection reveals only role, locale and expiry, never the organization, tenant, address or any account. An address that already has a DivalHR identity gets `409 INVITATION_CANNOT_BE_ACCEPTED` without a reason, and the invitation stays pending.
- **Email verification (guardrail 1).** The new identity is created with `emailVerified=true` only because the invitee proved control of the mailbox by presenting the single-use token that was sent to it. No other path sets it. The invitee then chooses a password through the identity provider's own `UPDATE_PASSWORD` email.
- **Rate limiting (A4).** The in-process limiter (10 requests per client per minute, 600 in total per minute, `429 RATE_LIMITED` with `Retry-After`) is defense in depth only. **Limiting `/api/v1/public/**` at the ingress or WAF is mandatory in production.** The client address comes from the socket; `X-Forwarded-For` is honored only when the direct peer is one of `DIVALHR_TRUSTED_PROXIES` (exact addresses, empty by default), and then the right-most untrusted hop is used. Headers from untrusted peers are ignored (fail closed), so rotating them never evades the limit. Client addresses are never logged or used as metric tags; the limiter keys on an HMAC under a random key that is replaced every window, and the `divalhr.ratelimit.rejections` metric is tagged by bucket only.
- **Acceptance.** A short lease serializes concurrent acceptances of one token; the identity-provider call runs outside any transaction; completion requires the same lease owner, so a worker whose lease expired can never commit (guardrail 5). A reconciler completes or compensates acceptances interrupted by a crash without creating a second identity, and retries the password email durably (guardrail 4).

### Identity-provider provisioning (MVP-010, narrowed by Issue #31)

The Core API creates identities with the confidential client `divalhr-core-provisioner` (client credentials; secret from `DIVALHR_KEYCLOAK_PROVISIONER_SECRET`, refused when missing or `dev-only-` outside development). Since Issue #31 it holds **no Keycloak admin permission at all**: no `realm-management` role and no fine-grained admin permission. Its only right is the client role `divalhr-provisioning/provision-invitations`, which lets it call the narrow Keycloak extension `divalhr-provisioning` (ADR 0006, contract `packages/shared-contracts/openapi/keycloak-provisioning.yaml`).

- **Three operations, keyed by invitation.** Create (or confirm) the invitation's identity; send its setup email, or confirm that setup is complete; delete it while it is pristine (compensation). Each acts only on the single user whose admin-only attribute `divalhr_invitation_id` equals the invitation ID; zero matches and more than one match are handled explicitly, and more than one fails closed without any change. There is no read, search or by-subject operation.
- **Authorization before input (A2).** Token signature, type, expiry, issuer and audience `divalhr-provisioning`; `azp` is the enabled confidential provisioner client; the caller is that client's live, enabled service account; the account currently holds the capability, checked on the live model (effective roles), never from token claims alone; the realm is enabled in the extension configuration. Only then are the path validated, the body read (creation only: at most 2048 bytes counted while streaming, `application/json`, one object, strict fields; credential setup and compensation take no body) or identities looked up. Unauthorized callers get the same detail-free 401 or 403 whatever the path, body or identity state.
- **Server-decided values.** The extension maps the role to its group through a closed table and sets `enabled`, `emailVerified`, exactly `tenant_id`, `divalhr_invitation_id` and `locale`, and the role's required actions (`UPDATE_PASSWORD`, plus `CONFIGURE_TOTP` for tenant administrators). Callers cannot supply groups, roles, attributes, credentials, flags or actions; `platform-admin` and the MFA marker role are rejected like any unknown role, so the provisioner can never grant them (guardrail 2). The tenant comes from the invitation row, which the Core derived from a verified token. The extension never updates an existing user: a replay with another tenant, role or address is a conflict. A new identity receives no realm default role and no default group, so a later change to the realm's defaults can never widen it; its rights come from its role group alone (PR #32 review). `realm:verify` (rule `invitation-groups-least-privilege`) fails if either invitation group grants more than its tenant role (plus the MFA marker for tenant administrators), directly, through composites or through client roles.
- **Concurrency.** Identical concurrent creates never conflict: a call that loses the race settles from committed state in a fresh transaction and confirms the same identity; only if that state cannot yet show the outcome does it answer the retryable `503 IDENTITY_BUSY`. `IDENTITY_CONFLICT` is reserved for a proven differing binding, and the Core treats any other 409 or 5xx as "provider unavailable": the invitation stays open and the invitee or the reconciler retries; it is never denied.
- **Setup states (A1).** The caller never names the role: the extension derives it from the identity's membership of exactly one approved role group, and none or both is `SETUP_STATE_INVALID`. Completed only for the role's proven terminal state (employee: one password and no pending action; tenant administrator: one password, one authenticator, no pending action); a consistent in-progress state sends another action email; a tenant administrator with the password done and the authenticator still pending is in progress (approved in the PR #32 review); anything else (partial, contradictory, extra credentials or actions, no or several role groups) is `SETUP_STATE_INVALID`. The Core records an invalid state as `FAILED` at once, never as sent, with an error log and the `invalid_state` metric outcome; a realm administrator investigates.
- **Compensation** deletes only a pristine identity (no credential, exactly its initial actions). A refusal is logged as `invitation_accept_compensation_refused`, counted, and left to a realm administrator; it never loops.
- **Evidence.** Each authorized operation records a Keycloak admin event (operation, outcome, invitation, tenant and correlation IDs, target user once resolved; never a representation) and a sanitized `divalhr.provisioning` log line. Refused callers are logged with a reason code only. No email address, username, token, credential, link or body is ever recorded.

The Issue #31 takeover (stolen provisioner secret: delete an enrolled administrator's authenticator, then send a setup link) is closed: the Admin API answers 403 to every such call, the extension refuses setup links and deletion for an enrolled administrator, and the realm verification fails if any broad right reappears (`provisioner-has-no-broad-admin-rights`, final mode). The secret must still be stored and rotated like a privileged credential: with it, an attacker could still create identities (only inside the two tenant-role groups, only for addresses that have no identity, without any credential), send another setup email for an identity whose setup is pending (to the invitee's own address), or delete an identity that is still pristine. Each of these leaves admin-event evidence, and none of them yields a credential or a session.

### First tenant administrator (MVP-014)

A platform administrator invites the first `tenant-admin` of an existing active organization; that person then invites everyone else. Architecture decision and amendments A1-A8 on Issue #38 apply.

- **Endpoints and target.** `GET`, `POST`, `POST …/revoke` and `POST …/resend` on `/api/v1/organizations/{organizationId}/tenant-admin-bootstrap` are platform-scoped (`@PlatformScoped`, `platform-admin`, exact MFA) and authorized before the path or body is read. The target comes only from the path and is resolved through `OrganizationDirectory`; the caller's `tenant_id` claim never participates (A4). A malformed, unknown or non-active organization gives the same `404 ORGANIZATION_NOT_FOUND`, and the raw value never reaches logs, metrics, audit or storage.
- **Rule (D-B2).** A bootstrap is possible only while the organization has no `tenant-admin` membership and no open (`PENDING` or `ACCEPTING`) tenant-administrator invitation of any origin; otherwise a generic `409 TENANT_ADMIN_BOOTSTRAP_UNAVAILABLE`. The role is fixed to `tenant-admin`; the body is exactly `{email, locale}`. The status response shows only whether a bootstrap is available and the open bootstrap invitation's receipt: never members, addresses or other invitations.
- **One organization lock (A1).** Every path that can create a tenant administrator takes the same locks in the same order: (0) the bootstrap actor's advisory lock (bootstrap create only), (1) the `tenant.organization` row `FOR NO KEY UPDATE` with a local `lock_timeout` (`DIVALHR_TENANT_ADMIN_LOCK_TIMEOUT`, default 5 s), (2) the tenant's invitation advisory lock, (3) invitation rows, (4) membership writes. Tenant-admin invitations, bootstrap create, resend and revoke, and tenant-admin acceptance all re-check their predicates under the lock; employee invitations take only (2). A lock timeout fails the request with no write, no email and no idempotency record.
- **Acceptance re-check (A2, D-B4 rejected).** Accepting a bootstrap invitation re-checks under the organization lock, before any identity-provider call, whether another tenant administrator now exists. If so the invitation ends `REVOKED` with the system marker `system:bootstrap-superseded` (allowed only for `PLATFORM_BOOTSTRAP` rows, `ACCEPTING → REVOKED`), audit action `invitation.bootstrap-supersede` with reason `bootstrap_superseded`, an `identity.invitation-revoked.v1` event with reason `BOOTSTRAP_SUPERSEDED`, and the invitee sees the generic `INVITATION_INVALID`. The check runs again in the completing transaction; if an administrator appeared during provisioning, the new identity is compensated and nothing is committed.
- **Idempotency (A3).** The fingerprint covers the organization and the canonical payload; reusing a key for another organization or payload gives `409 IDEMPOTENCY_KEY_REUSED`. A lost response is replayed exactly; eight concurrent creates produce one invitation and one email.
- **Per-actor limit (A8).** At most `DIVALHR_BOOTSTRAP_PER_ACTOR_PER_HOUR` (default 5, range 1-50) bootstrap invitations per platform administrator per rolling hour, counted durably in the database under the actor's advisory lock (`429 RATE_LIMITED` with `Retry-After`). The development Compose stack raises it to 50 for repeated end-to-end runs.
- **Atomic evidence (A7).** The invitation, its audit event (`invitation.bootstrap-create`, `-resend`, `-revoke`, with the platform actor and correlation ID) and its outbox event commit in one transaction; if any of them cannot be written, nothing is committed and no email is sent. `origin` is added to the v1 event `data` (the envelope's `data` is open). No address, token, subject or organization name appears in logs, metrics, audit metadata or events.
- **Tenant side.** Tenant administrators see the bootstrap invitation with its origin and may revoke it, but never reissue it (`409 TENANT_ADMIN_BOOTSTRAP_UNAVAILABLE`). A bootstrap never sets a password or authenticator: the invitee completes acceptance, password and TOTP in Keycloak through the narrow provisioning extension (Issue #31).

### Membership authority (MVP-012A)

`identity.tenant_membership` is the Core-side authority for tenant access (architect decisions on #37: D1, A1-A3, M1-M11, A12A-1 and A12A-2). Effective tenant access is the **intersection** of the verified access token and the caller's active membership; a role or `tenant_id` granted only in Keycloak gives no Core access.

- **Gate.** `ScopeAuthorizationInterceptor` checks, before any argument, query or body binding: (1) verified subject, (2) the required token role, (3) the verified tenant, (4) exact MFA for privileged roles, then (5) the membership through the platform port `MembershipAuthority` (implemented by the identity module). The membership must belong to the token's tenant and carry **exactly** the required role (no role hierarchy). A role-less tenant operation accepts a membership whose role the token also holds. A missing, foreign-tenant or wrong-role membership returns the ordinary `403 ACCESS_DENIED` with no membership-specific detail; the security log records `reason=membership_mismatch` with no subject, tenant or membership ID. A password-level privileged caller still gets `MFA_REQUIRED` first. "No detail" means no intentional response or control-flow disclosure; database authorization is not constant-time.
- **Scope.** Every `@TenantScoped` handler is gated (a reflective test covers current and future handlers). Platform-scoped, public, status and management paths perform no membership lookup. Method security (`@PreAuthorize`) stays token-based behind the gate.
- **Session.** `GET /api/v1/session` needs no MFA. Tenant roles are token ∩ membership; `platform-admin` comes from the token only and is never derived from a membership; a platform administrator's tenant claim grants no tenant role. A platform-administrator token without a tenant claim gets `tenantId: null`; any other token without a valid tenant keeps `TENANT_CONTEXT_MISSING`. The response never says why a role is missing.
- **Freshness.** No cross-request cache: each gated request reads committed state, so a membership change applies at the next request. A Keycloak role removal or user disable applies when the current access token expires (300 s in the development realm) or is refreshed (refresh tokens are revoked).
- **Fail closed.** A lookup failure returns `500 INTERNAL_ERROR` before the handler runs; no cached or default answer is used.
- **Single predicate.** One active-membership predicate (`JdbcMembershipRepository.ACTIVE`) is used by the gate, the session and the MVP-014 bootstrap rule (and by the 12B review). The lifecycle story (S3) narrows it in that one place.
- **Suspension and revocation.** There is no membership lifecycle write yet (S3). Emergency removal: a realm administrator disables the user and logs out their sessions in Keycloak (new tokens stop at once; existing access tokens lapse within their lifetime). Deleting a membership row by hand is not a supported operation: it bypasses audit and would reopen the MVP-014 bootstrap of an organization that loses its last administrator.
- **Address.** The membership keeps its source invitation's normalized address (confidential; never logged or returned by these endpoints). See `DATA-MODEL.md` (V10).
- **Rollout (A7).** Before a shared environment runs 12A: MVP-014 is deployed; `pnpm membership:preflight` (read-only, counts and IDs only; credentials from the environment only) reports no blocking category (for enabled tenant-role users: missing membership, tenant or role mismatch, or a missing or malformed `tenant_id`); discrepancies are resolved through supported operations (MVP-014 bootstrap, MVP-010 invitation, Keycloak role or attribute fixes) or an explicitly reviewed migration. There is no runtime bypass, shadow mode or off switch. Rolling the application back restores token-only authorization: a security downgrade that needs an incident-style change approval.

### Access review (MVP-012B)

Tenant administrators review who holds DivalHR access in their organization (architect decisions on #37: D4-D8, A4-A6, R1-R8, B1-B5). Read-only: there is no grant, revoke, export or scoped assignment.

- **Endpoints.** `GET /api/v1/access-review/entries`, `POST /api/v1/access-review/lookup` and `GET /api/v1/access-review/summary`, all `@TenantAdminOperation` with exact MFA and the 12A membership gate, checked before any binding. Every query uses the 12A active-membership predicate, so the review, its summary and the gate never disagree.
- **Inherited views.** Every membership is organization-wide. A `legalEntityId` or `siteId` filter (at most one) is first checked in the caller's tenant through `OrganizationUnitDirectory`; a missing and a foreign unit give the same 404. Every member is then returned with `matchedUnit.inheritance = INHERITED_FROM_TENANT`.
- **Pagination (B3).** Keyset on `grantedAt` then `membershipId`, both descending; page size 1-50 (default 25). Cursors are HMAC-bound to the operation, tenant, role filter, unit type, unit ID and page size (absent values encoded as `-`) and verified before any membership query. Pagination is stable and duplicate-free under concurrent inserts but is not a snapshot: a membership added after the first page may be missing from that traversal and appears on a fresh review.
- **Exact lookup.** POST body `{"email"}` only; normalized like invitations and matched through the keyed lookup in the caller's tenant. A non-member, an unknown address and another tenant's member give the same empty page. The submitted address is never echoed; a match without a recorded address returns `email: null`. No partial or prefix search.
- **Fail-closed disclosure audit (A4, R8, B2).** Each 200 (including an empty lookup and the summary) is built inside one transaction that writes `access-review.read` (actor, tenant, resource `access-review` = the organization, correlation ID, metadata `view`, `filterKinds`, `page`, `resultCount`, `digestVersion`). The body is serialized only after that transaction commits; an audit or commit failure gives `500 INTERNAL_ERROR` with no review data. Validation, authorization, unit-not-found and rate-limit failures disclose nothing and write no `access-review.read` row; authorization and first rate-limit denials are recorded as denial evidence instead (MVP-013).
- **Digest v1 (R1, B1).** `after_state_sha256` is the lower-case SHA-256 of these exact UTF-8 bytes, every line ending with LF including the last, no blank lines:

  ```text
  DIVALHR-ACCESS-REVIEW-DIGEST
  version=1
  view=<list|lookup|summary>
  page=<first|next|single>
  more=<true|false>
  count=<n>
  m=<membership id>            one per entry, response order (list, lookup)
  role=tenant-admin;n=<n>      summary only
  role=employee;n=<n>          summary only
  ```

  UUIDs are canonical lower case and integers plain decimal. `AccessReviewDigestTest` pins golden vectors; any structural change needs a new version. The digest is tamper-evidence of what was disclosed, not a reconstruction of past access.
- **Rate limit (D5, R2, B5).** 30 review requests per minute per subject across the three operations (`DIVALHR_ACCESS_REVIEW_REQUESTS_PER_MINUTE`), counted after successful 12A authorization and before binding, so authorized malformed requests count and unauthorized ones do not. `429 RATE_LIMITED` with `Retry-After` = the rest of the fixed window. In-process per instance: the effective cluster ceiling is 30 × active instances; a shared or durable limiter is a production-scaling follow-up.
- **Caching.** `Cache-Control: private, no-store` on every response of the three paths, including 400, 403, 404, 429 and 500. The web page fetches with `cache: 'no-store'` and keeps filters, lookup input, cursors and IDs in component state only.
- **Observability allow-list (B4).** Logs (`divalhr.access-review`), the metric `divalhr.access_review.requests{view, filter_kind, outcome}` and audit metadata carry only view, filter kinds, page, result count, digest version and outcome (bounded closed sets). Never an address, address lookup, subject, membership ID, unit ID, cursor, lookup input, role filter value or response body; the audit row's standard actor and tenant columns are the only accountability identifiers.

### Authorization denial audit (MVP-013)

Denied attempts at privileged operations by a verified identity leave append-only evidence in `platform.authorization_denial` (V12), in addition to the security log and metrics (Issue #43, decisions D1-D11, amendments A13-1 to A13-6). It proves that an identity attempted a privileged operation and was denied. It never stores request content, targets or claims, never changes a public response and never grants access.

- **Scope (D9).** All 25 privileged operations: the 5 `@PlatformScoped` operations and the 20 `@TenantAdminOperation` operations. A reflective test enumerates them and fails on any new privileged handler without coverage.
- **Eligible stages (D2, A13-3).** In gate order, before any argument, query or body binding:

  | Stage | Public response (unchanged) | Durable row | Tenant column |
  |---|---|---|---|
  | No, invalid or expired token | `401` | No (resource server; not attributable) | - |
  | 1. Missing or blank `sub` | `403 ACCESS_DENIED` | No (log and `ineligible` metric only) | - |
  | 2. Role missing | `403 ACCESS_DENIED` | `role` | none |
  | 3. Tenant missing or invalid (tenant scope) | `403 TENANT_CONTEXT_MISSING` | `tenant_context` | none |
  | 4. Exact MFA missing | `403 MFA_REQUIRED` + RFC 9470 challenge | `mfa` | none |
  | 5. Membership missing, foreign or wrong role | `403 ACCESS_DENIED` (identical to stage 2) | `membership` | none |
  | 6. Per-subject limit (access review) | `429 RATE_LIMITED` + `Retry-After` | `rate_limit`, first refusal per subject and window only | effective tenant |
  | 7. Method security denies after the interceptor allowed | `403 ACCESS_DENIED` | `method_security`, only with proven provenance | effective tenant (tenant scope) |

  Post-binding denials (`TENANT_ACCESS_DENIED`, foreign-parent `404`s, validation errors), the membership-lookup `500`, the MVP-014 business limit and `/session` are out of scope.
- **Row (D1, A13-5).** `id`, `occurred_at`, `actor_subject` (exactly the verified JWT `sub`: unchanged, no length limit because token validation imposes none, non-blank in the application and non-empty in the database), `action` = `authorization.denied`, `operation` (server-owned annotation value), `scope` (`platform` or `tenant`), `stage`, `tenant_id`, `correlation_id`. There is no metadata column. Database checks and the application record (`AuthorizationDenial`) enforce the same closed sets. A subject PostgreSQL text cannot hold (U+0000) is treated as ineligible rather than transformed.
- **Tenant rule (D8).** `tenant_id` is the effective tenant (verified token tenant confirmed by an active membership), so it is present only for tenant-scoped `rate_limit` and `method_security` rows. Before the membership gate the token's tenant may be foreign and is never recorded; platform rows never carry a tenant, even when the token has an incidental `tenant_id`.
- **Independent transaction (D3, A13-6).** `DenialAuditStore` owns a dedicated bulkhead: a Hikari pool `divalhr-denial-audit` of 2 connections (`connection-timeout` 1 s, `statement_timeout` and `lock_timeout` 2 s) with its own `DataSourceTransactionManager`, used explicitly through a `REQUIRES_NEW` template. Neither is a bean, so the application's `DataSource`, transaction manager and `AuditRecorder` (still `MANDATORY`) are unchanged. A denial row survives a rolled-back outer transaction. Allowed requests and budget-suppressed denials never touch the bulkhead.
- **One attempt per request.** The first call for a request marks it; later calls do nothing.
- **Method-security provenance (D5, A13-1).** `MethodSecurityDenialMarker` is the `AuthorizationEventPublisher` Spring method security reports to; it marks the request only when method security itself denies a method carrying `@PlatformScoped` or `@TenantScoped`. Only such a request, already allowed by the scope interceptor, produces a `method_security` row, the `divalhr.authorization.drift{scope, operation}` metric and an `authorization_drift` error log. A plain `AccessDeniedException` from a controller, service or framework component is never drift. No stack trace, message or argument is inspected.
- **Storage failure (D4).** The request stays denied with its normal response, status, body, challenge and `Retry-After`. The gap is signalled by `divalhr.authorization.denial_audit{outcome="failed"}` and one `denial_audit_failed` error log (stage, scope, operation, exception type and correlation ID; never the subject or exception message). Durability is not claimed while storage is unavailable, and there is no retry queue. Worst-case added latency on a denial is about 3 seconds.
- **Flood bounds (D6, A13-2).** Per fixed one-minute window and instance: 20 rows per verified subject (`DIVALHR_DENIAL_AUDIT_PER_ACTOR_PER_MINUTE`) and 600 rows in total (`DIVALHR_DENIAL_AUDIT_PER_INSTANCE_PER_MINUTE`); the cluster ceiling is the value × active instances. Budgets are checked before any connection is requested. Subjects are tracked under a per-window HMAC pseudonym (at most 10,000 per window), so nothing carries over between windows or restarts. Denials over a budget are **not** written: they appear only in the `suppressed` metric. Durable rows prove the recorded denials, not every attempt.
- **Telemetry (D11).** `divalhr.authorization.denial_audit{outcome, stage, scope}` with `outcome` in `written`, `suppressed`, `failed`, `ineligible`. Security log lines gain `audit=<outcome>` (`not_first` for later rate-limit refusals) and stage 3 now has its own `tenant_context_missing` line and `denied` metric. No log or metric names the actor: the stage-2 line no longer carries `actorSubject`. Logs and rows join on the correlation ID, which callers may choose within its format and is therefore a join key, not evidence.
- **Retention (D7, A13-4).** Append-only: triggers reject `UPDATE`, `DELETE` and `TRUNCATE`. No legal or business retention period is approved yet, so nothing is deleted and no archive or purge job exists; 13 months online is only a proposal. Removing evidence requires a separately reviewed archive or purge story.
- **Rollback.** `db/rollback/V12__rollback.sql` restores V11 exactly but refuses while any row exists; there is no override. Destroying evidence is not an application rollback: it needs a verified export (row count and checksum recorded), a recorded change approval and a separate reviewed change executed by an operator.

#### Runbook: denial audit

- **`failed` > 0 (alert, page).** Access is still denied; evidence for those denials is missing. Check database availability, locks on `platform.authorization_denial` and the `divalhr-denial-audit` pool (2 connections). The gap window is visible in the metric; the matching `authorization_denied` log lines (stage, operation, correlation ID, no actor) are the only remaining trace. No backfill is possible.
- **`suppressed` > 0 (warning).** One subject is producing many denials, or the instance ceiling was reached. Find the subject in recent rows (`actor_subject`, `occurred_at`), then revoke the session in Keycloak or the membership in the Core. Raise budgets only with review.
- **`divalhr.authorization.drift` > 0 (alert).** A privileged handler's `@PreAuthorize` and the scope interceptor disagree. Fix the annotation and redeploy; the reflective tests must cover the handler.
- **Capacity (warning at 1 GB or 5× the 7-day row-rate baseline).** At the default ceiling an instance writes at most about 0.86 million rows a day. There is no deletion schedule; report sustained growth so a retention decision can be made.

### Employee import (MVP-020)

Tenant administrators create employees from a CSV file in two steps: upload and check, then commit (Issue #45, approved proposal with amendments A20-1 to A20-6). Six `@TenantAdminOperation` operations under `/api/v1/employee-imports`: `employee-import.template`, `.create`, `.read`, `.rows`, `.commit` and `.discard`. All of them check exact MFA and the 12A membership gate, then the request limits, before any argument or body is read; denials and the first rate-limit refusal of a window are recorded as denial evidence (MVP-013).

- **Upload handling (A20-5, A20-6).** The request body is the CSV itself (`text/csv`). Multipart is disabled for the whole application (`spring.servlet.multipart.enabled: false`) and any other media type is `400 VALIDATION_FAILED` on `Content-Type`, checked only after authorization. The body is read as a stream capped at 2 MiB (`413 IMPORT_FILE_TOO_LARGE` after at most one 8 KiB buffer beyond the cap) within 30 seconds (`408 IMPORT_UPLOAD_TIMEOUT`); it is decoded as strict UTF-8 (a byte-order mark is ignored) and never stored. 2 MiB is a conservative transport cap, not a worst-case calculation: the row limit (1,000), the line limit (4,096 characters) and the column limit (20) bound the work independently.
- **CSV parsing (A20-3).** Apache Commons CSV 1.14.1 (RFC 4180 format, no escape character, no comments, no lenient end of file, no trailing data) behind the people-module port `CsvRecordSource`, which enforces the DivalHR subset. The delimiter (semicolon or comma) is chosen from the header line only. Fuzz tests (2,000 random inputs) and bounded-memory tests (an endless body; worst-case 2 MiB files whose allocation stays linear in the input) are part of the suite.
- **Row rules (A20-6).** Cells are normalized to NFC and runs of space separators collapsed; control, format, separator, unassigned, surrogate and private-use characters are rejected (`ROW_CONTROL_CHARACTER`). Lengths count Unicode code points after NFC: 160 for any cell, 100 for names. A value starting with `=`, `+`, `-` or `@` is rejected (`ROW_FORMAT`), so a stored value can never become a spreadsheet formula. Names start with a letter and contain only letters, combining marks, spaces, apostrophes, periods and hyphens. The database enforces the same grammar (`people.person_name_valid`, R20-1), so no write path can store a name the import would refuse. Dates are ISO `YYYY-MM-DD` from 1900 to 2999 only. Unit codes are matched in the caller's tenant through the `OrganizationPlacementDirectory` port; an unknown and a foreign code are the same `ROW_UNIT_NOT_FOUND`.
- **Staging and commit.** Valid rows are staged as normalized values for 2 hours; invalid rows keep only column keys and error codes, never their values. The commit repeats the preview digest and valid-row count it was shown (`409 IMPORT_PREVIEW_CHANGED` otherwise) and, when some rows are invalid, an explicit acknowledgement. One transaction locks the import, re-validates every valid row against the tenant's current employees and units, inserts employees and employments in employee-number order, writes audit and outbox records, marks the rows and erases every staged value. Any change since the preview, including a concurrent import taking an employee number, rolls everything back with `409 IMPORT_STALE`; nothing is ever partially committed. Upload and commit are idempotent: the same key with the same bytes or command replays the original response.
- **Request limits (A20-4).** Per subject, 10 requests per minute shared by upload and commit (`DIVALHR_EMPLOYEE_IMPORT_REQUESTS_PER_MINUTE`). Per tenant, 30 uploads (`DIVALHR_EMPLOYEE_IMPORT_TENANT_UPLOADS`) and 60 commits (`DIVALHR_EMPLOYEE_IMPORT_TENANT_COMMITS`) per 10 minutes. The buckets are independent: another administrator of the same tenant is not limited by the first one's subject bucket, and the tenant bucket applies across all administrators. `429 RATE_LIMITED` with `Retry-After`. At most 3 open imports per tenant (`409 IMPORT_LIMIT_REACHED`). Limits are in-process per instance: the cluster ceiling is the value × active instances. A shared limiter is a production-scaling follow-up.
- **Timeouts (A20-5).**

  | Stage | Limit | Response |
  |---|---|---|
  | Idle connection or stalled body between packets (Tomcat `connection-timeout`) | 20 s | connection closed |
  | Whole upload body | 30 s | `408 IMPORT_UPLOAD_TIMEOUT`, nothing created |
  | Validation and staging: statement / transaction | 5 s / 15 s | `503 IMPORT_TIMEOUT`, nothing created |
  | Commit: statement and lock / transaction | 10 s / 30 s | `503 IMPORT_TIMEOUT`, nothing created, the import stays open |
  | Expiry and retention jobs: statement | 10 s per batch of 100 | logged, retried on the next run |
  | Reverse proxy (recommendation) | request body ≥ 2 MiB plus headroom, read timeout ≥ 60 s | - |

  Failures before the transaction starts (authorization, limits, media type, body, file-level problems) create nothing and leave no staged data. Failures after it starts roll it back completely; a retry with the same idempotency key then succeeds.
- **Privacy (A20-1, A20-2).** Audit metadata carries only counts and versions: `employee-import.create`, `.commit`, `.discard` and `.expire` hold `totalRows`, `validRows`, `invalidRows` or `createdCount` and `notImportedCount`; each `employee.create` holds `importId` and `version`, and its `after_state_sha256` is a hash of the created state. Outbox events `people.employee.created.v1` (`employeeId`, `employmentId`, `importId`) and `people.employee-import.completed.v1` (`importId` and the counts) carry no name, employee number, start date or placement. API results never return employee IDs and never map a row to an employee. Logs and metrics carry counts and bounded codes only. Responses are `Cache-Control: private, no-store`; the web page keeps the file, rows and IDs in memory only.
- **Retention (A20-2).** Staged values are erased at commit, discard or expiry (2 hours). Closed import records and their row results (row numbers, statuses and error codes) are deleted 30 days after closing by default (`DIVALHR_EMPLOYEE_IMPORT_RESULT_RETENTION`, 1-90 days). This is an operational policy, not a statutory retention period. Retention never touches employees, employments, audit events or outbox events.
- **CSV output rule.** Every CSV DivalHR writes (today: the template) goes through `CsvCells`: each cell is quoted and a leading `=`, `+`, `-`, `@`, tab or carriage return is neutralized with an apostrophe.
- **Encryption at rest (proposal, production gate).** Employee numbers and names are Confidential; employment dates and placement are Restricted HR (staged values inherit their field's class). Before real HR data, storage encryption for the database volume and backups must be confirmed (see Production gates).
- **Rollback.** `db/rollback/V13__rollback.sql` restores V12 exactly but refuses while any people row exists; removing employee data is a separately reviewed operator change, never an application rollback.

#### Runbook: employee import

- **`503 IMPORT_TIMEOUT` repeatedly.** Look for long-running transactions or locks on `people.employee`, `people.employee_import` and the tenant's organization units. Nothing was created; the administrator retries with the same file.
- **`409 IMPORT_LIMIT_REACHED`.** The tenant has 3 open imports. They are cancelled from the page, or expire after 2 hours.
- **`employee_import_job_failed` warnings.** The expiry or retention job failed (for example a statement timeout). It retries on its next run (1 minute for expiry, 1 hour for retention). Open imports that are past their expiry are already refused by every operation.
- **Rate limits.** `429` responses are expected under bulk use; raise the limits only with review.

### Employee directory and employment history (MVP-021)

Tenant administrators read and change employment history (Issue #47, approved proposal H1-H20 with amendments M21-1 to M21-5). Nine `@TenantAdminOperation` operations under `/api/v1/employees`: `employee.list`, `employee.search`, `employee.read`, `employee.timeline`, `employment-change.list`, `employment-change.preview`, `employment-change.create`, `employment-change.cancel-preview` and `employment-change.cancel` (privileged operations: 31 → 40). Exact MFA and the 12A membership gate are checked, then the request limits, before any argument or body is read; denials are recorded as denial evidence (MVP-013). Employee and change IDs are resolved in the verified tenant only: unknown, foreign and malformed IDs give the same `404`.

- **Disclosure audit (H15 under M21-1).** Every read and preview is a disclosure of Confidential or Restricted HR data: the query and one audit event run in one transaction, and the body is returned only after both committed (fail-closed, as the MVP-019 access review). The action is the operation; the resource is `organization`/tenant (directory, search) or `employee`/employee ID. Metadata is exactly `{view, page, resultCount, schemaVersion}`: no search text, filter, employee data or result ID. `after_state_sha256` is a digest of the disclosed IDs in order.
- **Write audit and outbox (M21-1).** Actions `employment-change.schedule` (effective after the business date), `.apply` (on or before it), `.correct` and `.cancel`, resource `employment-change`/change ID. Metadata is exactly `{schemaVersion, rowsSuperseded, rowsCreated, employmentVersion}`; `after_state_sha256` is the digest of the whole active timeline after the write. Outbox `people.employment.changed.v1` and `people.employment.change-cancelled.v1` carry exactly `{employeeId, employmentId, changeId}` (for a cancellation, the cancelled change) with the envelope's schema version. Names, numbers, dates, units, managers, reasons and categories never appear in metadata, event data, logs or metrics.
- **Preview binding (H9, M21-2).** A commit repeats the preview's `expectedVersion` and digest (`previewDigest`, or `cancellationDigest` for a cancellation). The transaction takes the tenant's manager-graph lock when a manager row is involved, locks the employment row, checks the version (`409 EMPLOYMENT_VERSION_CONFLICT`), recomputes and re-validates everything, and compares the digest (`409 EMPLOYMENT_PREVIEW_CHANGED`). Writes are idempotent (`Idempotency-Key`; replays return the original response).
- **Business rules.** The business date is today in the organization's IANA time zone. Changes before it are retroactive: they need a reason and `acknowledgeRetroactive`, and must start within the configurable window (`DIVALHR_EMPLOYMENT_RETROACTIVE_DAYS`, 60 by default, 0-366: a pilot business rule, not a statutory period). Corrections need a correction reason and their row must end within the window. Only an active scheduled `CHANGE` can be cancelled; restoration is bounded by the next active row and never alters a later change (`409 EMPLOYMENT_CHANGE_HAS_DEPENDENTS` otherwise). Placements are checked through the tenant module's port (units exist, match their parents and are in effect over the whole period); managers must be other employees of the tenant, employed over the whole period, without loops or chains over 50 levels.
- **Database authority (M21-4, M21-5, R21-1).** PostgreSQL enforces immutable history, single-move supersession with same-employment ownership, no deletes or truncation, non-overlap, gap-free placement, the manager-cycle rule under its own advisory lock, and the exact shape of every change, even for writes that bypass the service. The shape is revalidated whenever an assignment is later inserted or superseded in the name of an existing change, and a change or cancellation must touch exactly its kinds. Only the named constraints map to business codes (`MANAGER_INVALID` for the cycle and depth rules, `EMPLOYMENT_PREVIEW_CHANGED` for overlap and coverage, `EMPLOYMENT_CHANGE_NOT_CANCELLABLE` for a second cancellation); anything else stays `500`.
- **Request limits.** Per subject: `employee-read` 60 per minute for reads, searches and previews (`DIVALHR_EMPLOYEE_READ_REQUESTS_PER_MINUTE`; the development Compose stack sets the per-subject MVP-020 and MVP-030 buckets to five times their defaults (contract-expiration stays 60) because the parallel browser suite shares the seed administrators, DEVX-001A); `employment-change` 20 per minute for writes (`DIVALHR_EMPLOYMENT_CHANGE_REQUESTS_PER_MINUTE`). Per tenant: `employee-search` 300 per 10 minutes (`DIVALHR_EMPLOYEE_SEARCH_TENANT_REQUESTS`) and `employment-change-write` 200 per 10 minutes (`DIVALHR_EMPLOYMENT_CHANGE_TENANT_WRITES`). In-process per instance, as MVP-020.
- **Timeouts.** Writes: 5 s per statement and lock, 15 s per transaction (`divalhr.employment-history`); a timeout rolls everything back with `503 EMPLOYMENT_CHANGE_TIMEOUT` and a retry with the same key succeeds.
- **Caching and browser state.** Every response is `Cache-Control: private, no-store`. Search text travels only in a `POST` body; the only identifier in a page URL is the employee ID. The web pages keep queries, previews and cursors in memory only.
- **Rollback (M21-3).** `db/rollback/V14__rollback.sql` restores the V13 application schema exactly but refuses once any history beyond the hire exists; there is no override. It never edits `flyway_schema_history` and never drops `btree_gist`.

#### Runbook: employment history

- **Rolling back V14.** Prefer rolling back the application only. If the schema must go back: stop the application, run the rollback (it refuses once history exists), then, as a separate reviewed operator step, delete the `14`, `14.1` and `14.2` rows from `flyway_schema_history` before deploying the previous application version. Leave `btree_gist` installed; it may be shared and V12/V13 ignore it.
- **`btree_gist` missing on a managed database.** V14 creates it when the migration role owns the database (trusted extension). Otherwise provision it beforehand as an administrator (`CREATE EXTENSION btree_gist`), as `infrastructure/docker/postgres/20-provision-extensions.sh` does for compose.

- **`409 EMPLOYMENT_VERSION_CONFLICT` or `EMPLOYMENT_PREVIEW_CHANGED`.** Expected under concurrent edits of one employee: the page asks for a new preview.
- **Unexpected `500` on a write.** A database constraint outside the mapped set fired (for example `employment_change_shape`): this is a defect, not a user error. Collect the correlation ID; the transaction was rolled back.

### Separation and access revocation (MVP-022)

Tenant administrators separate employees and link employee records to DivalHR access (Issue #49, approved proposal with amendments A22-1 to A22-6; ADR 0008). Eleven `@TenantAdminOperation` operations: `employee-separation.preview`, `.create`, `.read`, `.cancel-preview`, `.cancel`, `separation-task.update` and `access-revocation.retry` under `/api/v1/employees/{employeeId}/separations`, and `employee-access-link.read`, `.lookup`, `.create` and `.remove` under `/api/v1/employees/{employeeId}/access-link`. Authorization (role, exact MFA, membership) and the request limits run before any argument or body is read; reads and previews share the MVP-021 `employee-read` bucket and writes the `employment-change` buckets.

- **Exact DivalHR denial.** A separation with linked access writes an `identity.access_revocation` with `effective_at`: the start of the day after the last day in the organization's time zone, or the commit instant for `IMMEDIATELY`. `IMMEDIATELY` is allowed only when the last day is today or earlier and needs the `IMMEDIATE_ACCESS_REMOVAL` acknowledgement; a past last day forces it (A22-1). The membership gate, the session endpoint and the access review share one predicate (no non-cancelled revocation with `effective_at <= statement_timestamp()`), so the first request after that instant is refused with the generic `ACCESS_DENIED` whatever Keycloak does. `tenant_membership` stays immutable.
- **Protected principals.** A tenant administrator's access is never revoked here: the separation is refused (`409 SEPARATION_PROTECTED`, `reason` `ADMIN_ACCESS`), and the database only accepts revocations of `employee` memberships (composite key and `CHECK`). An administrator cannot separate the employee linked to their own access (`reason` `SELF`).
- **Linking.** The membership is chosen by its exact address (POST body only, HMAC lookup in the caller's tenant; never echoed, logged or listed). One active link per employee and per membership; a link cannot be removed while a separation holds it (`409 ACCESS_LINK_LOCKED`), and a revoked membership cannot be linked again.
- **Durable identity-provider revocation.** `AccessRevocationJobs` calls the provisioning extension's `PUT …/tenants/{tenantId}/identities/{subject}/access-revocation` (disable, remove online and offline sessions, set not-before) with retries from 1 to 60 minutes over 10 attempts, then `MANUAL_INTERVENTION`. Before every call it revalidates under the revocation row lock that the revocation is due and unchanged, that its original link still binds the same employee and membership, and that the membership is still an employee membership of the tenant; the subject is read from the membership at that moment. Otherwise it makes no call and records `STALE_LINK`, `MEMBERSHIP_CHANGED` or `TENANT_MISMATCH` (A22-5). The extension independently refuses any identity that is not an employee identity it created for the path tenant (`409 REVOCATION_REFUSED`, nothing changed).
- **Transaction boundary (A22-4).** `EmployeeSeparationService` is the only coordinator; identity ports join its transaction (`MANDATORY`) and the global lock order of ADR 0008 applies to every path. A separation, its report changes, its reminders and its revocation commit or roll back together.
- **Preview binding.** Commits and cancellations repeat the preview's `expectedVersion` and digest, which covers the employee's rows, the blockers, every affected direct-report interval and the count, the link and its version, the access instant and the checklist; anything else is `409 SEPARATION_PREVIEW_CHANGED` or `EMPLOYMENT_VERSION_CONFLICT`. Writes are idempotent (`Idempotency-Key`).
- **Audit and outbox (A22-6).** Reads and previews are fail-closed disclosures. Write actions: `employee-separation.record`, `.cancel`, `.effective`, `separation-task.update`, `employee-access-link.create`, `.remove`, `access-revocation.request`, `.cancel`, `.retry`, `.idp-succeeded`, `.idp-failed`, `.manual-intervention` and `tenant-membership.access-revoke`. Metadata holds only `schemaVersion`, counts, versions, closed states, attempts and outcome codes; the confirmed digest (or a digest of identifiers) is in `after_state_sha256`. Outbox data is identifiers only (`people.employment.separation-recorded|cancelled|effective.v1`, `people.separation-task.updated.v1`, `identity.employee-access-link.created|removed.v1`, `identity.membership.access-revoked.v1`); Keycloak outcomes are never published.
- **Caching and browser state.** Every response is `private, no-store`; the web page keeps the address, previews and results in memory only.

#### Runbook: separations and access revocation

- **Alerts.** Page on `divalhr_access_revocation_open{state="manual"} > 0` and on `divalhr_access_revocation_open{state="overdue"} > 0` (a pending revocation older than 30 minutes). `divalhr_access_revocation_total{outcome}` counts transitions and outcomes (`activated`, `revoked`, `absent`, `refused`, `unavailable`, `attempts_exhausted`, `stale_link`, `membership_changed`, `tenant_mismatch`, `busy`, `lease_lost`). Logs carry job names, counts and outcome codes only.
- **The access window.** From `effective_at` every Core call is refused. Until the job completes, the person may still sign in to Keycloak and see an empty shell whose every call returns 403; the page says "sign-in removal in progress".
- **`MANUAL_INTERVENTION`.** DivalHR access is already denied. Read the outcome code on the separation page or in `identity.access_revocation.outcome_code`. `REFUSED`: the Keycloak user is not an employee identity created by the extension for this tenant (for example a hand-made account, or a changed group): disable it in the Keycloak admin console if appropriate, after checking it is the right person. `ATTEMPTS_EXHAUSTED`/`UNAVAILABLE`: fix Keycloak reachability, then use **Retry** on the page (a fresh budget of 10 attempts). `STALE_LINK`, `MEMBERSHIP_CHANGED`, `TENANT_MISMATCH`: the binding changed after scheduling; investigate before any manual action and never disable an identity whose link you have not confirmed.
- **Reconciliation.** A completed revocation means the Keycloak user is disabled with no sessions. Re-enabling a person is an identity-administration act outside DivalHR and is not undone by any rollback.
- **`503 EMPLOYMENT_CHANGE_TIMEOUT` on a separation or cancellation.** A lock was busy (for example the worker holding the revocation row): nothing was written; retry.
- **Rolling back V15.** `db/rollback/V15__rollback.sql` refuses while any separation, task, link or revocation exists, or any employment has an end date; then, as for V14, delete the `15` row from `flyway_schema_history` as a separate reviewed step. It never re-enables a Keycloak user.

### Contracts and acknowledgement (MVP-030)

Tenant administrators manage contract templates and issue contracts; employees acknowledge their own contracts (Issue #51, approved proposal D1–D16 with amendments A30-1 to A30-4; ADR 0009). Fifteen `@TenantAdminOperation` operations under `/api/v1/contract-templates` and `/api/v1/employees/{employeeId}/contracts` (buckets `contract-read` 60/min and `contract-write` 20/min per subject, `contract-write` 200 per 10 min per tenant) and three `@EmployeeSelfOperation` operations under `/api/v1/me/contracts` (`contract-self` 30/min per subject). Authorization and limits run before any argument or body is read.

- **Employee self-service.** `@EmployeeSelfOperation` = `@TenantScoped(role = "employee")` plus method security; no MFA, which employees do not use. After the revocation-aware membership gate, every query is bound to the caller's own active employee-access link, read through the identity port in the same transaction (`FOR SHARE`). No link: `403 EMPLOYEE_LINK_REQUIRED`. Another employee's or tenant's contract, a malformed and an unknown ID: the same `404 CONTRACT_NOT_FOUND`. Administrators have no self-service path, and there is no offline acknowledgement (D6).
- **Durable denial evidence (A30-1).** The administrator operations join MVP-013 evidence (`platform.authorization_denial`, every stage). The scope interceptor and the method-security drift handler now write a row only for a privileged role (`platform-admin`, `tenant-admin`); employee self-service denials, `EMPLOYEE_LINK_REQUIRED` and self-service `404`s go to the security log and `divalhr_employee_self_service_denials_total{operation,reason}` only (closed label values). No existing handler changed behaviour: every earlier tenant handler is privileged.
- **Safe templates (A30-2).** Grammar v1 is plain text; URI schemes (any case, fullwidth, zero-width or space-split), `//` and `\\` paths, web addresses, percent, entity and backslash escapes, Markdown links and images, and HTML or event attributes are refused at draft validation with `422 CONTRACT_TEMPLATE_INVALID` (closed `reason`, `line`), never echoing the text. Rendering parses before substituting; values are literal; the web renders text nodes only.
- **Integrity (A30-4).** Domain-separated, versioned SHA-256 digests for the template text, snapshot, preview, statement and evidence; the server recomputes and compares every client value in constant time and stores none; version columns are pinned by `CHECK = 1`. Issue repeats the preview's employment version and digest (`409 CONTRACT_PREVIEW_CHANGED`); acknowledgement repeats the snapshot and statement digests and versions (`409 CONTRACT_ACKNOWLEDGEMENT_CHANGED`, wrong versions `400`).
- **Immutability.** Approved and retired template versions, issued contracts (apart from `ISSUED → ACKNOWLEDGED|VOID`), guard rows and evidence are protected by triggers; nothing can be truncated; only never-approved drafts are deleted. An acknowledged contract is never voided.
- **Terminology (A30-3).** An acknowledgement records only that the authenticated employee made the stated confirmation of the displayed snapshot. It is not an electronic signature; no label, enum or description claims one.
- **Evidence (D12).** Contract, employee, membership, link, snapshot digest and versions, statement code, version, language and digest, database time and correlation ID. No IP address, user agent, image, biometrics or national ID.
- **Audit and outbox.** Previews and reads are fail-closed disclosures (`contract.preview`, `contract.read`, `contract.self-read`); template reads hold no personal data and are not disclosure-audited (D14). Write actions: `contract-template.create`, `contract-template-version.create|update|delete|approve|retire`, `contract.issue`, `contract.void`, `contract.acknowledge`, and `contract-integrity.check` (FAILURE, per mismatch). Metadata holds only `schemaVersion`, versions, closed states and counts; the body, snapshot or evidence digest (or a digest of identifiers) is in `after_state_sha256`. Outbox data is identifiers and `schemaVersion` only (`documents.contract-template.version-approved|version-retired.v1`, `documents.contract.issued|acknowledged|voided.v1`).
- **Caching and browser state.** Every response is `private, no-store`; pages keep templates, previews, contracts and statements in memory only; URLs carry opaque IDs only.

#### Runbook: contracts

- **Alerts.** Page on `divalhr_contract_integrity_total{outcome="mismatch"} > 0` and on sustained `5xx` of `contract.*` operations. The integrity job runs daily (`DIVALHR_CONTRACT_JOBS_ENABLED`); it is read-only and never repairs.
- **An integrity mismatch.** Treat as a security incident: the stored digest no longer matches the stored text, or the structured copy differs. Find the contract by the ID in the `contract_integrity_mismatch` log line or the FAILURE audit event; do not edit the row. Compare with the latest backup, preserve both, and escalate. After any database restore, run the job and confirm zero mismatches.
- **`503 CONTRACT_TIMEOUT`.** A lock was busy (a concurrent separation, issue, void or unlink): nothing was written; retry.
- **An employee sees `EMPLOYEE_LINK_REQUIRED`.** Their membership is not linked to their employee record: link it from the employee record (MVP-022). Access ends at a separation's revocation instant.
- **Statement wording (D16).** Version 1 of the acknowledgement statement is approved provisionally; the organization's counsel must review it before production use. A wording change is statement version 2 (code, migration and ADR), never an edit of version 1.
- **Rolling back V16.** `db/rollback/V16__rollback.sql` refuses while any template, version, guard, contract or acknowledgement row exists; there is no override, because issued contracts and evidence are never erased. Then remove the `16` row from `flyway_schema_history` as a separate reviewed step, together with an application rollback.

### Contract expiration queue (MVP-031A)

Tenant administrators see which contracts end soon or have ended (Issue #73, approved proposal with amendments A31A-1 to A31A-6). Two read-only `@TenantAdminOperation` operations: `contract-expiration.search` (`POST /api/v1/contract-expirations/search`) and `contract-expiration.summary` (`GET /api/v1/contract-expirations/summary`), with the per-subject bucket `contract-expiration` (60/min, `DIVALHR_CONTRACT_EXPIRATION_REQUESTS_PER_MINUTE`) on both, and on the search also the tenant bucket `employee-search` (300 per 10 min). Authorization and limits run before any argument or body is read; denials leave MVP-013 evidence.

- **Tenant only from the verified JWT.** The tenant is never a request field. Employments come from the people module through the platform port `EmploymentExpirationScope`, in the same `REPEATABLE READ` transaction; the documents module never names people tables (architecture test). A unit of another tenant matches nothing.
- **Cursors (A31A-4).** HMAC-signed and bound to the operation, tenant, business date, a SHA-256 of the search text, the unit, the sorted categories and the page size. A cursor reused with any other filter, tenant or size gives `400 CURSOR_INVALID`. The business date is pinned in the cursor, so a traversal never changes date, never repeats a row and keeps its category boundaries; eligibility can still change between requests, and rows added after the cursor position can appear. It is not a frozen snapshot.
- **Audit (A31A-6).** Both reads are fail-closed disclosures (`contract-expiration.search`, `contract-expiration.summary`): if the audit row cannot be written, nothing is returned. Metadata is `schemaVersion`, `view`, `page`, `resultCount` and the closed `filterKinds`; the search digest hashes the business date, counts and returned contract IDs, and the summary digest hashes only its own payload. No names, numbers, search text, unit or cursor are stored or logged.
- **Data minimisation.** Items carry the contract UUID only as a link key; the web never displays it as a contract number. Employee numbers and names appear only in the response body (`private, no-store`) and in-memory page state; the search text is sent in a `POST` body, never in a URL.
- **Index (V17).** `contract_coverage_order` serves the queue; `db/rollback/V17__rollback.sql` drops it and has no data effect.

## Privileged multifactor authentication (MVP-011)

Every interactive holder of `platform-admin` or `tenant-admin` completes TOTP, and the Core API enforces it independently. SMS and email codes are never a privileged factor; passkeys are a future, stronger option.

### Evidence the Core accepts

- **Claim.** The access token's `acr`, which Keycloak computes from the level of authentication the session achieved. The only accepted value is the scalar string `urn:divalhr:loa:mfa` (exact, case-sensitive). A missing claim, `urn:divalhr:loa:pwd`, Keycloak's legacy `"0"`/`"1"`, other strings, arrays, numbers and objects all fail closed.
- **Never evidence.** The privileged role itself, the marker role `divalhr-privileged-mfa`, `amr`, an OTP credential being configured, required actions, `tenant_id`, invitation or membership state, headers or frontend flags. The marker role grants no authority in the Core and is filtered from its authorities; it never appears in API responses, logs, audit or the UI.
- **Order.** For every `@PlatformScoped` and `@TenantAdminOperation` handler, `ScopeAuthorizationInterceptor` checks the verified subject, the role, the tenant (tenant operations), then the assurance, all before argument, query or body processing. Method security additionally requires the `ASSURANCE_MFA` authority, which `KeycloakRealmRoleConverter` adds only for the exact `acr`.
- **Denial.** `403 MFA_REQUIRED` with empty params and `WWW-Authenticate: Bearer error="insufficient_user_authentication", acr_values="urn:divalhr:loa:mfa"` (RFC 9470), identical for platform and tenant operations apart from the route and correlation ID. One `divalhr.security` warning with `reason=mfa_required`, operation, scope, required role, result and correlation ID; no subject, `acr` value, token or request data (A5). The `outcome=mfa_required` metric counts it. Durable denial auditing remains MVP-013.
- **Not affected.** `GET /session` (password assurance is enough), the status endpoint, public invitation endpoints (bearer tokens are not read) and employee operations.
- **Contract.** Privileged operations carry `x-divalhr-required-assurance: mfa` and the `PrivilegedForbidden` 403; `ApiContractDriftTest` fails if that set differs from the privileged handlers.

### Keycloak configuration

- **Browser flow** `divalhr browser`, bound as the realm browser flow so it covers every browser client: level 1 is the password; level 2 runs only for the marker role (implied by both privileged roles, including through role groups) and asks for the TOTP code. A privileged user without an authenticator is **denied** with a French or English message (`divalhrMfaEnrollmentRequired`); there is no self-enrollment at sign-in (D3).
- **Client `divalhr-web`:** `acr.loa.map` `{"urn:divalhr:loa:pwd":1,"urn:divalhr:loa:mfa":2}`, `default.acr.values` and `minimum.acr.value` `urn:divalhr:loa:mfa`. A request for the password level cannot skip the code of a privileged user; employees still end at level 1.
- **TOTP policy:** HmacSHA1, 6 digits, 30 seconds, one period of skew, codes not reusable.
- **Brute force:** 5 failures, then a wait growing by 60 seconds up to 15 minutes; never permanent (D7). Keycloak's quick-login check also applies.
- **Session:** a level-2 session keeps `acr` `mfa` across refreshes for the SSO session (at most 10 hours, 30 minutes idle, D4). The level's max age (10 hours) is enforced at the next authorization, not retroactively on refresh (guardrail 6). Fresh step-up for sensitive operations is future work.
- **Enrollment:** invited tenant administrators receive one action link for `UPDATE_PASSWORD` and `CONFIGURE_TOTP`; employees for `UPDATE_PASSWORD` only. The provisioner uses its existing permissions only.
- **Role changes:** a user promoted inside a password session keeps `acr` `pwd` on refresh, so the Core answers `MFA_REQUIRED` until a new authorization steps up (or denies an unenrolled user). A removed role disappears from the next token.
- **`admin-cli`** stays enabled for the development `kcadm.sh` runbook (A1). Its tokens carry no Core audience, roles, tenant or `acr` and are rejected by the Core. In production, Keycloak administration has its own MFA, a restricted network and monitored admin events; disabling `admin-cli` is not required.
- **Events:** login events and admin events are enabled; admin-event representations are not stored because they may contain personal data.
- **Verification:** `pnpm realm:verify` checks a running realm read-only and prints rule names with PASS or FAIL only (A4; Keycloak README).

### Web behaviour

The web app sends privileged requests with its in-memory token. On `403 MFA_REQUIRED` it signs in again with `acr_values=urn:divalhr:loa:mfa` and returns to the same page. It does this once per signed-in session: if the Core still refuses after a step-up, an MFA-required page explains the situation in French or English, offers a user-initiated retry and lost-device guidance, and never loops through the identity provider.

### Recovery, bootstrap and break-glass

- **Lost or replaced authenticator (A2).** Only an authorized Keycloak realm administrator may reset a factor, after verifying the person's identity through an independent channel. They remove the OTP credential, send an action link with `CONFIGURE_TOTP`, revoke the user's sessions, and also require a password reset when compromise is suspected. Admin events record the change. This is a Keycloak administration task, not a DivalHR platform operation; an in-app or delegated reset needs its own story. There are no recovery codes (D2).
- **First platform administrator:** created by the realm administrator in Keycloak with a setup link for `UPDATE_PASSWORD` and `CONFIGURE_TOTP`. Without an authenticator, no privileged sign-in is possible.
- **First tenant administrator (MVP-014):** always invited by a platform administrator through the bootstrap endpoints, never created by hand in Keycloak.
- **Break-glass:** there is no MFA-exempt DivalHR account. Recovery goes through the Keycloak administrator, whose own account is protected by MFA.
- **Provisioner (D6a, closed by Issue #31).** The provisioner can no longer delete or reset any credential, send action emails through the Admin API, or change any user; see the identity-provider provisioning section above.

### Development fixtures

The three privileged seed users carry published, visibly labelled `dev-only-totp-…` TOTP seeds (D11), valid only in the development realm; `DevelopmentRealmBoundaryTest` enforces the prefix and that only privileged seed users have one. Tests compute codes in memory. Playwright traces, screenshots, videos and failure page snapshots are off, so codes and the authenticator setup page never reach artifacts (guardrail 5).

**Browser-suite SSO reuse (DEVX-001A, A75-3).** The `features` Playwright project reuses one real password-and-TOTP sign-in per privileged seed role. `auth-setup` saves only that role's Keycloak SSO cookies (`KEYCLOAK_IDENTITY`, `KEYCLOAK_SESSION`) of the identity host, never application tokens or browser storage, into a per-run directory created with `mktemp` outside the repository and every report path (directory `0700`, files `0600`). The state is treated as a credential: it is never printed, uploaded or copied into evidence, and the global teardown and the runner's `trap` remove it. Each feature test still signs in through Authorization Code + PKCE. A hygiene check over the run's generated output (not the repository, whose development fixtures are public) fails on a JWT, a session-cookie value, a seed password or TOTP seed, a TOTP code of the run, or a leftover state directory. Genuine MFA, wrong and replayed codes, membership changes and sign-outs stay in the serial `identity` project.

## Pagination cursors

List endpoints return opaque keyset cursors: `base64url(payload) "." base64url(HMAC-SHA256(payload))`. The payload holds a version, the last row's code and id, and a SHA-256 binding of the operation, verified tenant and filters (for sites, the legal entity; for teams, the parent type and parent id). Cursors are therefore unusable across tenants, operations or parents.

- Decoding rejects input longer than 512 characters or of the wrong shape before decoding, verifies the MAC in constant time before parsing, and accepts only the exact allow-listed fields and types. Every failure is the same `400 CURSOR_INVALID` with no params.
- Cursors, payloads, bindings and the key are never logged.
- The key comes from `DIVALHR_CURSOR_SIGNING_KEY` and fails closed: start-up is refused when it is missing or shorter than 32 bytes, and outside `development` when it is a published `dev-only-` value. `.env.example` holds only an obvious development placeholder.
- **Known limitation:** there is a single key and no rotation. Changing it invalidates outstanding cursors (clients restart from the first page). Key rotation with a key identifier is future work before production.

## Idempotency

Retryable creates require `Idempotency-Key`. Records are scoped to `(operation, verified JWT sub, key)`, store only successful responses, and are written in the same transaction as the business change, audit event and outbox event. They are retained for at least the configured period (`divalhr.idempotency.retention`, default 7 days) and honoured until a cleanup job removes them; cleanup must never delete a record before its `expires_at`.

Sensitive events include actor, action, tenant, object, result, time, reason, correlation ID, and an integrity-protected reference to relevant before-and-after values.
