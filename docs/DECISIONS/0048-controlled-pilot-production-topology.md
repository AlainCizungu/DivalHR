# ADR 0048: Controlled-pilot production environment and operational readiness (LAUNCH-002, Issue #230)

Status: proposed with the PR for Issue #230 (the architect-approved implementation contract). Builds on ADR 0004 (AWS target), ADR 0046 (privacy governance), ADR 0047 (commercial website) and the OPS-001 test environment. This is an engineering and operational framework, not legal advice, certification or a contractual service-level commitment.

## 1. Boundary (read first)

This story **builds and proves a production platform**. It does not onboard a customer, activate a real statutory pack or retention policy, connect a real payment, credit, insurance, telecom or accounting partner, or declare DivalHR generally available. Those are separate, explicit launch decisions (LAUNCH-003 and the founder).

Nothing in this PR provisions anything: no AWS resource, DNS record, certificate, provider account or deployment exists after the merge. Each of those is a separately approved execution step. The environment, once built, stays behind a **launch lock** (section 2, L2-12) that is closed by default.

## 2. Decisions

- **L2-1 Domains.** `https://divalhr.com` is the commercial website; `https://www.divalhr.com` redirects to it; `https://app.divalhr.com` is the authenticated application with `/api`, `/identity`, `/ai` and the authentication routes beneath it. The commercial page may also be served at `app.divalhr.com/` for signed-out visitors, with canonical metadata pointing to `https://divalhr.com`. `hr-dev.dival.ai` stays synthetic-only and is never promoted. The web application learns the two origins from public runtime configuration (`DIVALHR_PUBLIC_ORIGIN`, `DIVALHR_APP_ORIGIN`); when they are unset (every other environment) behaviour is unchanged.
- **L2-2 Single-host topology.** One region. An internet-facing Application Load Balancer (ACM TLS) with AWS WAF in front of one dedicated EC2 application host in a private subnet. Administration only through AWS Systems Manager Session Manager and Run Command. Caddy/web, Core, AI, Keycloak, PostgreSQL run as isolated containers on that host. No Mailpit, no seed account, no synthetic provider or receiver. Encrypted EBS root and data volumes, an encrypted versioned S3 bucket for logical backup copies, an encrypted S3 bucket with Object Lock for evidence, encrypted EBS snapshots (DLM) as secondary recovery.
- **L2-3 Network.** Only the load balancer is public, on 443 (80 redirects at the load balancer). The host security group accepts one application listener, only from the load balancer's security group, and has no inbound SSH rule. **Egress is deny by default**: the host reaches AWS services only through VPC endpoints (Systems Manager, Secrets Manager, KMS, CloudWatch, ECR, S3 gateway) and the Amazon SES SMTP interface endpoint (private DNS, endpoint security group, submission port only). No internet gateway, NAT or default route exists for the private subnet, so no CIDR-based egress exists either. Real payment, lending, insurance, telecom and accounting egress is therefore impossible, not merely unconfigured.
- **L2-3a Images (consequence of deny-by-default egress).** The production host cannot reach public registries, so it **never builds**. Release images are built by `ops/production/build-push.sh` on an operator-controlled build machine (the verification host or a workstation with Docker) from `git archive` of the release commit, never from a working tree, tagged with the full commit SHA, and pushed to a private immutable-tag ECR repository; the host pulls them through the ECR and S3 endpoints. Third-party base images (Caddy, PostgreSQL) are mirrored into that repository by digest by `ops/production/mirror-images.sh`, which refuses a copy whose digest differs from the pin in the Compose file. This replaces hr-dev's build-on-host and is the main operational difference from the test environment.
- **L2-4 Ingress and abuse controls.** WAF: the AWS managed common and known-bad-inputs rule groups, a body-size constraint aligned with the application, a rate-based rule on `/api/v1/public/` (per client address as seen by the load balancer, never from a client-supplied forwarded header), and a stricter rate-based rule for abusive traffic. WAF logging is on and redacts the body (not logged by WAF), `authorization`, `cookie`, `x-hub-signature-256`, `idempotency-key`, `x-divalhr-signature`, and the URI query string. The application limiter stays enabled.
- **L2-5 Secrets.** Source of truth: AWS Secrets Manager (KMS key of this environment) under `divalhr/production/`. They are materialised on the host only as root-controlled files under the encrypted data volume, mounted read-only; none is an environment variable of a container, in Git, CI output, evidence or chat. Keys are separate by purpose. Development and test prefixes and missing secrets are refused. Backups never contain the secret store; the recovery runbook restores secrets independently.
- **L2-6 Identity.** A production realm template rendered at first start: privileged MFA exact, no users except the provisioner service account, exact redirect URIs and web origins, secure cookies, admin console not publicly routed. The bootstrap administrator is a one-time credential removed after a named operator exists. Realm verification runs in final production mode before the release is accepted.
- **L2-7 Transactional e-mail.** Core already reads provider-neutral SMTP settings (`DIVALHR_MAIL_*`, password as a config-tree file); the realm template takes the same provider values. The provider is Amazon SES, reached only through its VPC SMTP endpoint; production mail configuration is pinned to `email-smtp.<region>.amazonaws.com` of the deployment region and an SES SMTP port, and `prod_load_mail` refuses anything else. The verified sending identity, its DNS (SPF, DKIM, DMARC), SES production access and SMTP credentials are operator prerequisites outside Git. Until they are configured the launch lock reports `email: NOT_CONFIGURED` and onboarding stays refused; the environment can still be provisioned and tested with a Dival-owned mailbox once configured.
- **L2-8 Data.** Production databases, roles, keys and backups are production-only. Nothing is copied from hr-dev. Initial data is the platform configuration and one synthetic acceptance tenant. LAUNCH-001 retention policy mechanisms stay inactive and no purge runs.
- **L2-9 Backup and recovery.** Internal engineering targets, not an SLA: recovery point at most 24 h, recovery time at most 8 h in a staffed exercise. Nightly encrypted logical dumps of Core and Keycloak with a checksum manifest, copied off the host to versioned S3; encrypted EBS snapshots; a restore drill into an isolated environment proving the restored databases share the release and migration state; a quarterly runbook and an evidence template. The first deployment is not accepted until one complete drill passes.
- **L2-10 Release and rollback.** The hr-dev model, extended: a full 40-character commit reachable from `origin/main`, all required checks green, **a fresh qualifying full verification of the production release** (hr-dev evidence alone is refused), checksummed read-only tree-bound evidence, a pre-deploy backup, migrations, health, OIDC and backchannel checks and a bounded synthetic smoke before the release is marked current; failure restores the previous release and both databases; one host-wide lock serialises deploy, backup, restore, rotation and recovery; the operator needs explicit founder approval and gets a redacted evidence package. The Mac-side tool ships the release through S3 and runs the host script through Systems Manager, because there is no SSH. No deployment from a working tree. A short maintenance window is accepted; there is no blue/green.
- **L2-11 Observability.** Monitoring that does not depend on the host being healthy: CloudWatch alarms and an external HTTPS check (Route 53 health check with certificate-expiry alarm) notifying an SNS topic whose subscription is `contact@dival.ai` (confirmed by the operator). Host, disk, memory, CPU, container health, backup age, restore-drill age, 5xx, identity failure, worker failure, WAF block rate, deployment and watchdog alarms. Metric dimensions never carry tenant, employee, e-mail, partner choice, token, code or free text. A correlation identifier is added at the load balancer and carried to the application without logging bodies.
- **L2-12 Launch lock.** An operator control on the host (`/srv/divalhr-prod/state/launch-lock`, plus an SSM parameter mirror) that is **CLOSED by default**, checked by the deployment, the acceptance script and the onboarding checklist, and reported by the external check. While closed: no real organization, employee, import, statutory pack, retention policy, provider egress or payment/credit/insurance/telecom workflow. Lifting it needs a recorded founder authorization and leaves evidence; lifting is not part of this story.

## 3. Alternatives considered

1. **A second copy of the hr-dev stack promoted to production.** Rejected by L2-1: shared realms, secrets and data would break isolation.
2. **ECS/Fargate or EKS now (ADR 0004 target).** Rejected for the controlled pilot: more moving parts than the fastest responsible path needs. The single host keeps the proven Compose runtime and the hr-dev release evidence model; ECS/Fargate and a multi-AZ database remain the scale path.
3. **Public egress with an allow-list proxy.** Rejected: a proxy is another component to run and prove. VPC endpoints give deny-by-default with nothing extra to operate.
4. **Public SSH with a bastion.** Rejected: Session Manager needs no inbound rule and leaves an audit trail.
5. **Building on the host (as hr-dev does).** Rejected by L2-3a; it needs public registries.
6. **Blue/green or zero-downtime releases.** Rejected: a short documented window is acceptable for a pilot.

## 4. Accepted limitations (single-host pilot)

One host in one availability zone: a host or zone failure is a recovery (up to the 8 h target), not a failover. The database is on the host. Maintenance windows interrupt service. The load balancer to host hop is TLS to an internal-CA certificate that the load balancer does not validate; the hop stays inside private subnets. The recovery targets are demonstrated by the drill, not promised to customers. No SLA, uptime figure, capacity promise or compliance certification is made.

## 5. Path to scale

Multi-AZ RDS or a replicated PostgreSQL, ECS/Fargate or EKS with the same images and the same release evidence, a second host behind the same load balancer, a shared rate limiter, private object storage for receipts, and a managed secret rotation function. Each is a later story with its own approval.

## 6. Consequences

1. Production resources, secrets, realms, data and backup prefixes can never be shared with hr-dev: the policy tests fail if a name, path or prefix collides.
2. The first production deployment needs prerequisites outside Git (AWS account and region, hosted zone, ACM certificate, e-mail provider, alarm mailbox, a baked host image with Docker and the SSM agent). They are listed in `docs/OPS-PRODUCTION.md`; the story stops, fail closed, when one is missing.
3. Images are built once on an operator-controlled build machine; the host trusts only the ECR repository and the checksummed evidence.
